# Plan: Widget Runtime — prvctice as an AI App Builder

> STATUS: Planning document, not verified system documentation

## Context

prvctice has the infrastructure of an operating system: unified input routing, a skill execution runtime, a GPU compositor, a frame scheduler, and a recursive learning pipeline that generates skills from observed behavior. The existing "apps" (weather, notes, PDF viewer, games, pet, YouTube) are bespoke Vue components with no shared abstraction.

The first version of this plan got the direction wrong. It proposed "compound apps" that tile existing widgets together. Tim's feedback was clear: **the goal isn't rearranging what exists — it's expanding capability.** News feeds, photo editing, F1 schedules, piano keyboards, habit trackers, currency converters. Real interactive widgets with real data. The reference model is Nothing Playground: describe an app in natural language, get a functional widget.

prvctice's advantage over Nothing Playground: the recursive learning system can **propose** apps based on observed behavior, not just respond to prompts. Users get apps they didn't know they needed.

**Chat is out of scope for this plan.**

An **app** in prvctice is a sandboxed interactive widget that:

- Renders in a draggable, resizable window
- Communicates with the system through a bridge API (postMessage)
- Can access data connectors (weather, news, web, etc.) through the bridge
- Can invoke skills and AI inference through the bridge
- Is theme-aware (inherits prvctice's active theme colors)
- Can be generated by AI from a natural language description
- Can be proposed by the recursive learning system based on observed patterns

## Phase 1: App Definition Format + Bridge API

### What we're building

The foundational contract between apps and the system. Every app — whether hand-coded, AI-generated, or auto-proposed — speaks this protocol.

### App Definition Format

An app is defined by an `AppDefinition`:

```typescript
// web/types/apps.ts

interface AppDefinition {
  id: string; // unique identifier
  name: string; // display name
  description: string; // what it does (shown in gallery)
  icon: string; // Iconify icon name
  version: string; // semver
  source: 'builtin' | 'generated' | 'community' | 'discovered';

  // The actual app code
  component: AppComponent;

  // What system capabilities this app needs
  permissions: AppPermission[];

  // Window configuration defaults
  window: {
    width: number; // default width
    height: number; // default height
    minWidth?: number;
    minHeight?: number;
    resizable: boolean;
    position?: 'float' | 'dock-left' | 'dock-right' | 'center';
  };

  // Optional: skills this app exports (invocable by the skill system)
  exportedActions?: ExportedAction[];

  // Optional: what data connectors it uses
  connectors?: string[]; // connector IDs

  // Metadata for the gallery
  tags?: string[];
  thumbnail?: string; // base64 preview image
  createdAt: number;
  prompt?: string; // original prompt if AI-generated
}

// Component types — what the app actually is
type AppComponent =
  | { type: 'html'; code: string } // generated/community: self-contained HTML/CSS/JS, runs in sandboxed iframe
  | { type: 'vue-internal'; component: string }; // builtin only: references a registered Vue component name, renders directly (no iframe)
// NOTE: vue-sfc was considered but dropped. Compiling SFCs in a sandboxed iframe
// would require shipping the Vue compiler (~30KB) into every app. HTML apps cover
// 100% of generated/community use cases. vue-internal covers builtins that need
// direct Vue reactivity (Notes with TipTap, PDF with composables, etc.).

// Permissions the app can request through the bridge
// ENFORCEMENT: Every bridge request is checked against the app's granted permissions.
// The bridge handler calls permissionManager.check(appId, permission) before dispatching.
// If not granted, the request is rejected with { error: 'PERMISSION_DENIED' }.
type AppPermission =
  | 'connector:weather' // weather data                    [web + electron]
  | 'connector:news' // news/RSS feeds                  [web + electron]
  | 'connector:web-fetch' // fetch arbitrary URLs            [web + electron] (proxied through backend)
  | 'connector:location' // user's location                 [web + electron] (browser geolocation API)
  | 'connector:calendar' // calendar events                 [web + electron]
  | 'connector:storage' // persistent key-value for app    [web + electron] (always granted, no prompt)
  | 'connector:ai' // invoke LLM inference            [web + electron] (uses user's configured key)
  | 'connector:skills' // execute prvctice skills         [web + electron]
  | 'connector:time' // current time, timers            [web + electron] (always granted, no prompt)
  | 'connector:files' // read files from workspace       [electron only] — hidden on web
  | 'connector:clipboard' // read/write clipboard            [electron only] — hidden on web
  | 'theme:read' // read current theme colors       [web + electron] (always granted, no prompt)
  | 'theme:subscribe'; // get notified on theme changes   [web + electron] (always granted, no prompt)

// Permission grant model:
// - IMPLICIT grants (no prompt): storage, time, theme:read, theme:subscribe
//   These are safe, sandboxed, and every app needs them.
// - PER-APP grants (prompt on first use, persisted): all other permissions
//   Stored in IndexedDB: Map<appId, Set<AppPermission>>
//   User sees: "F1 Schedule wants to access Web Fetch. Allow?"
//   Grant is remembered for that app. User can revoke in settings.
// - PLATFORM-GATED: files, clipboard require Electron.
//   On web, these permissions are unavailable and hidden from the grant UI.
//   Apps requesting them on web get { error: 'PLATFORM_UNSUPPORTED' }.

interface PermissionGrant {
  appId: string;
  permission: AppPermission;
  grantedAt: number;
  platform: 'web' | 'electron' | 'both';
}

// web/services/apps/permissionManager.ts
interface PermissionManager {
  check(appId: string, permission: AppPermission): boolean;
  request(appId: string, permission: AppPermission): Promise<boolean>; // shows prompt
  revoke(appId: string, permission: AppPermission): void;
  getGrants(appId: string): AppPermission[];
  isPlatformSupported(permission: AppPermission): boolean;
}

interface ExportedAction {
  id: string; // action ID for skill system
  name: string; // display name
  description: string;
  params?: Record<string, 'string' | 'number' | 'boolean'>;
}
```

### Bridge API

Apps run in sandboxed iframes (`sandbox="allow-scripts"`, no `allow-same-origin`). They communicate with the system through `postMessage`. The bridge is the app's window into prvctice.

**Authentication model:** Since sandboxed iframes have `origin === "null"`, we can't rely on origin checks. Instead, each iframe gets a unique nonce at creation time. The nonce is injected into the SDK before `srcdoc` is set. Every message from the app must include this nonce. The parent validates both `event.source === iframe.contentWindow` AND `message.nonce === expectedNonce`. Messages failing either check are silently dropped.

**Permission enforcement:** Every bridge request is checked against the app's granted permissions via `permissionManager.check(appId, requiredPermission)`. If the permission isn't granted, the bridge returns `{ error: 'PERMISSION_DENIED', requestId }` without dispatching to the connector. The first request for an ungrantled permission triggers the grant prompt.

```typescript
// web/services/apps/bridge.ts

// ── HANDSHAKE PROTOCOL ──
// 1. Parent creates iframe with nonce injected into bridgeSDK
// 2. App sends: { type: 'bridge:hello', nonce }
// 3. Parent validates nonce + event.source, responds: { type: 'bridge:ready', appId, grantedPermissions, theme }
// 4. App is now live. All subsequent messages must include nonce.
// 5. Parent ignores any message before handshake completes.

// Every message from app includes nonce for auth
interface BridgeMessage {
  nonce: string; // per-iframe secret, validated on every message
}

// Messages FROM app TO system
type AppToSystem = BridgeMessage &
  (
    | { type: 'bridge:hello' } // handshake init
    | {
        type: 'connector:request';
        connector: string;
        method: string;
        params: any;
        requestId: string;
      } // data request
    | { type: 'storage:get'; key: string; requestId: string }
    | { type: 'storage:set'; key: string; value: any; requestId: string }
    | { type: 'storage:delete'; key: string; requestId: string }
    | { type: 'skill:execute'; skillId: string; params?: any; requestId: string }
    | { type: 'skill:list'; requestId: string } // list available skills
    | { type: 'ai:infer'; prompt: string; requestId: string }
    | { type: 'ai:chat'; messages: Array<{ role: string; content: string }>; requestId: string }
    | { type: 'theme:get'; requestId: string }
    | { type: 'theme:subscribe' } // start receiving theme:update
    | { type: 'app:resize'; width: number; height: number }
    | { type: 'app:title'; title: string }
  );

// Messages FROM system TO app
type SystemToApp =
  | { type: 'bridge:ready'; appId: string; grantedPermissions: AppPermission[]; theme: ThemeColors } // handshake response
  | { type: 'connector:response'; requestId: string; data: any; error?: string }
  | { type: 'storage:value'; requestId: string; value: any }
  | { type: 'skill:list:response'; requestId: string; skills: SkillSummary[] }
  | { type: 'ai:response'; requestId: string; text: string; error?: string }
  | { type: 'theme:current'; requestId: string; theme: ThemeColors } // response to theme:get
  | { type: 'theme:update'; theme: ThemeColors } // push on theme change
  | { type: 'action:invoke'; actionId: string; params?: any }
  | { type: 'app:focus' }
  | { type: 'app:blur' }
  | {
      type: 'error';
      requestId?: string;
      error: string;
      code: 'PERMISSION_DENIED' | 'INVALID_REQUEST' | 'CONNECTOR_ERROR' | 'PLATFORM_UNSUPPORTED';
    };

// Parent-side message handler pseudocode:
//
// window.addEventListener('message', (event) => {
//   // 1. Validate event.source matches a known iframe contentWindow
//   const appInstance = findInstanceBySource(event.source);
//   if (!appInstance) return;  // unknown source, drop silently
//
//   // 2. Validate nonce
//   if (event.data.nonce !== appInstance.nonce) return;  // wrong nonce, drop
//
//   // 3. If handshake not complete, only accept bridge:hello
//   if (!appInstance.handshakeComplete && event.data.type !== 'bridge:hello') return;
//
//   // 4. For connector/AI/skill requests, check permissions
//   const requiredPermission = getRequiredPermission(event.data);
//   if (requiredPermission && !permissionManager.check(appInstance.appId, requiredPermission)) {
//     // Trigger permission prompt, or return error
//     postToApp(appInstance, { type: 'error', requestId: event.data.requestId, error: 'Permission not granted', code: 'PERMISSION_DENIED' });
//     return;
//   }
//
//   // 5. Dispatch to appropriate handler
//   dispatch(appInstance, event.data);
// });

// ThemeColors — what the app receives
interface ThemeColors {
  name: string;
  primary: string;
  secondary: string;
  background: string;
  surface: string;
  text: string;
  textSecondary: string;
  accent: string;
  border: string;
}
```

### Bridge SDK (injected into apps)

A small JS library injected into each app's iframe before the app code runs. The SDK wraps `postMessage` into a clean async API and handles the handshake, nonce auth, and request/response correlation.

**Injection:** The runtime generates the SDK script with the nonce baked in, then prepends it to the app's HTML in `srcdoc`. The nonce is unique per iframe instance and never exposed to the app's own code — only the SDK uses it internally.

```typescript
// web/services/apps/bridgeSDK.ts
// This gets injected as a <script> into the iframe's srcdoc, with __NONCE__ replaced at injection time

// ── Internal: not exposed to app code ──
const _nonce = '__NONCE__'; // replaced by sandbox.ts at injection time
const _pending = new Map(); // requestId → { resolve, reject }
const _themeCallbacks = [];
let _ready = false;
const _readyCallbacks = [];

// postMessage wrapper — includes nonce on every message
function _send(msg) {
  window.parent.postMessage({ ...msg, nonce: _nonce }, '*');
}
function _request(msg) {
  const requestId = crypto.randomUUID();
  return new Promise((resolve, reject) => {
    _pending.set(requestId, { resolve, reject });
    _send({ ...msg, requestId });
    // Timeout after 30s
    setTimeout(() => {
      if (_pending.has(requestId)) {
        _pending.delete(requestId);
        reject(new Error('Bridge timeout'));
      }
    }, 30000);
  });
}

// Listen for responses from parent
window.addEventListener('message', (event) => {
  const msg = event.data;
  if (msg.type === 'bridge:ready') {
    _ready = true;
    _readyCallbacks.forEach((cb) => cb());
    _readyCallbacks.length = 0;
  }
  if (msg.requestId && _pending.has(msg.requestId)) {
    const { resolve, reject } = _pending.get(msg.requestId);
    _pending.delete(msg.requestId);
    if (msg.error) reject(new Error(msg.error));
    else resolve(msg.data ?? msg.value ?? msg.text ?? msg.skills ?? msg.theme ?? msg);
  }
  if (msg.type === 'theme:update') _themeCallbacks.forEach((cb) => cb(msg.theme));
  if (msg.type === 'action:invoke')
    window.dispatchEvent(new CustomEvent('prvctice:action', { detail: msg }));
});

// ── Public API: what apps see ──
window.prvctice = {
  // Lifecycle
  onReady: (callback) => {
    if (_ready) callback();
    else _readyCallbacks.push(callback);
  },

  // Data connectors — all return plain JSON objects (not Response objects)
  weather: {
    current: (location?) =>
      _request({
        type: 'connector:request',
        connector: 'weather',
        method: 'current',
        params: { location },
      }),
    forecast: (location?, days?) =>
      _request({
        type: 'connector:request',
        connector: 'weather',
        method: 'forecast',
        params: { location, days },
      }),
  },
  news: {
    headlines: (category?) =>
      _request({
        type: 'connector:request',
        connector: 'news',
        method: 'headlines',
        params: { category },
      }),
    search: (query) =>
      _request({
        type: 'connector:request',
        connector: 'news',
        method: 'search',
        params: { query },
      }),
    rss: (feedUrl) =>
      _request({
        type: 'connector:request',
        connector: 'news',
        method: 'rss',
        params: { feedUrl },
      }),
  },
  web: {
    // CRITICAL: Returns a serialized response object, NOT a Response.
    // Response is not structured-clonable and can't cross postMessage.
    // Returns: { status: number, headers: Record<string, string>, body: string | object }
    // If the response is JSON, body is pre-parsed. Otherwise body is a string.
    fetch: (url, options?) =>
      _request({
        type: 'connector:request',
        connector: 'web-fetch',
        method: 'fetch',
        params: { url, options },
      }),
  },
  time: {
    now: () => new Date(), // local, no bridge needed
    timezone: () => Intl.DateTimeFormat().resolvedOptions().timeZone, // local
  },
  location: {
    get: () =>
      _request({ type: 'connector:request', connector: 'location', method: 'get', params: {} }),
  },

  // Storage (per-app, persisted to IndexedDB on parent side)
  storage: {
    get: (key) => _request({ type: 'storage:get', key }),
    set: (key, value) => _request({ type: 'storage:set', key, value }),
    delete: (key) => _request({ type: 'storage:delete', key }),
  },

  // AI inference
  ai: {
    ask: (prompt) => _request({ type: 'ai:infer', prompt }),
    chat: (messages) => _request({ type: 'ai:chat', messages }),
  },

  // Skills
  skills: {
    execute: (skillId, params?) => _request({ type: 'skill:execute', skillId, params }),
    list: () => _request({ type: 'skill:list' }),
  },

  // Theme
  theme: {
    get: () => _request({ type: 'theme:get' }),
    onChange: (callback) => {
      _themeCallbacks.push(callback);
      _send({ type: 'theme:subscribe' });
      return () => {
        const i = _themeCallbacks.indexOf(callback);
        if (i >= 0) _themeCallbacks.splice(i, 1);
      };
    },
  },

  // Window
  window: {
    resize: (width, height) => _send({ type: 'app:resize', width, height }),
    setTitle: (title) => _send({ type: 'app:title', title }),
  },
};

// Initiate handshake
_send({ type: 'bridge:hello' });
```

**Serialization contract:** All data crossing the bridge must be structured-clonable (plain objects, arrays, strings, numbers, booleans, null). No `Response`, `Blob`, `File`, `ArrayBuffer`, or class instances. The bridge SDK and parent-side handler both enforce this. Specifically:

- `web.fetch` returns `{ status, headers, body }` — not a `Response` object
- `ai.ask/chat` returns a plain string
- All connector responses are plain JSON
- Errors are `{ error: string, code: string }` — not `Error` instances

### Security Model

**Three layers of defense:**

#### Layer 1: iframe sandbox

```html
<iframe sandbox="allow-scripts" srcdoc="..." />
```

`sandbox="allow-scripts"` only. **Never `allow-same-origin`** — with both flags set on same-origin content, the iframe can remove its own sandbox attribute and escape entirely.

#### Layer 2: Content Security Policy

CSP is enforced via a `<meta>` tag injected into every app's `srcdoc` by `sandbox.ts` before the app code runs:

```html
<meta
  http-equiv="Content-Security-Policy"
  content="
  default-src 'none';
  script-src 'unsafe-inline';
  style-src 'unsafe-inline';
  img-src data: blob:;
  font-src data:;
  connect-src 'none';
  frame-src 'none';
  object-src 'none';
  base-uri 'none';
"
/>
```

Key restrictions:

- **`connect-src 'none'`** — blocks `fetch()`, `XMLHttpRequest`, `WebSocket`, `EventSource` from inside the iframe. This is the critical control that forces all data access through the bridge.
- **`script-src 'unsafe-inline'`** — allows inline scripts (necessary for self-contained apps) but blocks `eval()` and `Function()` constructor. Note: `'unsafe-eval'` is NOT included.
- **`frame-src 'none'`** — no nested iframes.
- **`img-src data: blob:`** — allows data URIs and blob URLs for dynamically generated images (Canvas, WebGL). No network image loading.
- **`object-src 'none'`** — no plugins, Flash, etc.

#### Layer 3: Bridge authentication

Per-iframe nonce handshake (described above in Bridge API). Every message validated by `event.source` AND nonce. Permission enforcement on every request.

#### Layer 4: Static analysis (pre-execution)

Before an app's code is loaded into an iframe, `validator.ts` scans for forbidden patterns:

```typescript
// web/services/apps/validator.ts
const FORBIDDEN_PATTERNS = [
  /\beval\s*\(/, // eval()
  /new\s+Function\s*\(/, // new Function()
  /import\s*\(/, // dynamic import()
  /importScripts\s*\(/, // Web Worker imports
  /document\.cookie/, // cookie access attempts
  /window\.open\s*\(/, // popup attempts
  /window\.parent(?!\s*\.postMessage)/, // parent access (except postMessage)
  /window\.top/, // top frame access
  /navigator\.sendBeacon/, // data exfiltration
];

// Also check: the app's HTML must not contain its own <meta> CSP tag
// (which could weaken our injected CSP — last-wins for meta CSP)
const CSP_OVERRIDE_PATTERN = /<meta[^>]*content-security-policy/i;
```

#### What apps CAN do

- Render any HTML/CSS/JS (inline only)
- Use Canvas 2D, WebGL, Web Audio, Web Animations
- Call the bridge API for data, storage, AI, skills
- Respond to theme changes and action invocations
- Use `crypto.randomUUID()`, `crypto.getRandomValues()`

#### What apps CANNOT do

- Make any network requests (`connect-src 'none'` + sandbox)
- Access the parent DOM (`sandbox` + no `allow-same-origin`)
- Read cookies or localStorage of the parent
- Use `eval()` or `new Function()` (`script-src` without `'unsafe-eval'`)
- Load external scripts or images from URLs
- Access the file system or Node.js / Electron APIs
- Open popups or navigate the parent
- Modify other apps

#### Resource limits

- **Watchdog:** Parent pings iframe every 10s with `{ type: 'ping' }`. SDK auto-responds with `{ type: 'pong' }`. Three missed pongs → iframe killed + user notified.
- **Memory:** Monitor iframe via `performance.measureUserAgentSpecificMemory()` (Chrome 89+). Alert if > 50MB.
- **CPU:** If the iframe's thread blocks for > 5s (detected by missed pong), kill it.

## Phase 2: Data Connector Layer

### What we're building

The system-side services that fulfill bridge API requests. Each connector handles one data domain.

### Connectors

Connectors are split into two execution tiers based on whether they handle secrets (API keys) or can be served from the frontend.

```
── Frontend connectors (run in renderer process) ──
web/services/connectors/
├── index.ts              — connector registry + dispatch
├── timeConnector.ts      — time, timezone (no bridge needed, purely local)
├── locationConnector.ts  — browser geolocation API
├── storageConnector.ts   — per-app IndexedDB namespace
├── skillConnector.ts     — execute skills via skill coordinator
├── calendarConnector.ts  — iCal parsing (local .ics files)
├── clipboardConnector.ts — system clipboard (Electron IPC only)
└── filesConnector.ts     — read files from user workspace (Electron IPC only)

── Backend connectors (run on Express server, hold API keys) ──
src/routes/connectors/
├── weather.ts            — proxies to Open-Meteo (free, no key) or OpenWeatherMap (user key)
├── news.ts               — proxies to NewsAPI (user key) or RSS parser (no key, fallback)
├── webFetch.ts           — proxied HTTP requests with URL validation
└── ai.ts                 — routes through existing provider system (keys already on backend)
```

**Why the split:** Weather, news, web-fetch, and AI connectors all require either API keys or outbound HTTP requests. API keys must never be sent to the renderer process (where app iframes live). These connectors run on the backend, and the frontend bridge handler calls them via internal HTTP: `POST /api/v1/connectors/:connectorId/:method`.

Frontend connectors (storage, skills, time, location, calendar, clipboard, files) either access browser APIs directly or use Electron IPC. No secrets involved.

### Connector Interface

```typescript
// Shared interface — both frontend and backend connectors implement this
interface Connector {
  id: string;
  name: string;
  description: string;
  tier: 'frontend' | 'backend';
  platform: 'web' | 'electron' | 'both'; // platform availability
  methods: Record<string, ConnectorMethod>;
  requiresApiKey?: boolean; // user needs to configure (shown in settings)
  requiresPermission?: boolean; // user must approve first use
}

interface ConnectorMethod {
  name: string;
  params: Record<string, ParamDef>;
  returns: string; // TypeScript type description for documentation
  handler: (params: any, appId: string) => Promise<any>;
}

// Frontend bridge dispatches to the right tier:
// - Frontend connector: call handler directly
// - Backend connector: POST /api/v1/connectors/:id/:method
```

### Key Implementation Notes

**Weather:** Primary: Open-Meteo API (free, no key required, geocoding included). Fallback: OpenWeatherMap if user provides a key. Open-Meteo covers current conditions, hourly/daily forecasts, and historical data — more than enough for widgets. Backend-only (outbound HTTP).

**News:** Primary: Built-in RSS/Atom parser (no API key needed). Supports any RSS feed URL. Fallback: NewsAPI.org if user provides a key (free tier: 100 req/day, only for dev/personal use per their ToS). The RSS-first approach avoids ToS issues entirely and works without configuration. Backend-only (outbound HTTP).

**Web Fetch:** Backend-only. All requests are proxied through the Express server. Validation rules:

- URL allowlist: user can configure allowed domains in settings (default: open, except blocked list)
- Blocked: `localhost`, `127.0.0.1`, `0.0.0.0`, `::1`, `169.254.*`, `10.*`, `172.16-31.*`, `192.168.*` (no SSRF)
- Rate limit: 10 requests/minute per app (configurable)
- Max response size: 5MB
- Returns serialized `{ status, headers, body }` (not Response — see serialization contract)

**AI Inference:** Backend-only. Routes through existing provider system (Anthropic, Gemini, OpenRouter, LM Studio). Uses user's configured provider and API key (already stored on backend). Token limit per request: default 2,000 output tokens (configurable per app in settings).

**Storage:** Frontend. Each app gets its own IndexedDB namespace (`app:{appId}:*`). Quota per app (default 5MB). Keys are prefixed to prevent cross-app access. CRUD operations. Always granted (implicit permission).

**Files:** Frontend via Electron IPC only. Read-only access to user's workspace folder. File picker dialog for explicit selection. No write access from apps. Returns `null` on web platform.

**Clipboard:** Frontend via Electron IPC only. Read/write system clipboard. Returns `PLATFORM_UNSUPPORTED` on web.

## Phase 5: Migrate Existing Bespoke Widgets

### What we're building

Rewriting existing widgets (weather, games, notes, etc.) as apps on the new runtime. This proves the runtime works and gives users examples of what's possible.

### Migration Strategy

Each existing widget becomes a builtin AppDefinition. The Vue components stay mostly intact but get wrapped in the app model:

**Option A (quick): Wrap existing Vue components**

- Keep the existing Vue SFC
- Create an AppDefinition with `component: { type: 'vue-internal', component: 'WeatherTimeWidget' }`
- `vue-internal` apps render directly in the parent DOM (inside `AppWindow.vue`'s content slot) — no iframe, no sandbox
- This is safe because these are first-party builtin components, not generated code
- The `AppWindow.vue` component checks `app.component.type`: if `'html'` → render in sandboxed iframe; if `'vue-internal'` → render via `<component :is="..." />`
- Register with the app registry on startup
- Window manager handles positioning instead of per-widget magnetic attachment

**Option B (full): Rewrite as self-contained HTML apps**

- Rebuild each widget as a self-contained HTML app using the bridge API
- Proves the bridge API is sufficient for real apps
- More work but validates the architecture

### Recommended: Option A first, Option B selectively

Start with Option A for all widgets (quick win, zero feature loss). Then selectively rewrite the simpler ones (weather, games) as HTML apps to validate the bridge.

### Migration Order

1. **Weather/Time** → Most standalone, natural app. Rewrite as HTML app (validates bridge + weather connector).
2. **Games (Pong, Block Breaking, Slice Master)** → Already self-contained Canvas logic. Natural fit for HTML apps.
3. **Notes** → Wrap as Vue-internal app. TipTap dependency makes full rewrite complex.
4. **PDF Viewer** → Wrap as Vue-internal app. 1,700+ lines of composables, not worth rewriting yet.
5. **Model Viewer (Pet/Bird)** → Wrap as Vue-internal app. Three.js dependency.
6. **YouTube** → Wrap as Vue-internal app. Simple but iframe-in-iframe is tricky.

## Phase 8: Background Triggers & Daemons

### What we're building

Making the `trigger` skill type real. Right now it's a placeholder — the skill coordinator accepts trigger skills but execution just returns success and does nothing. This phase builds the daemon layer: skills that run in the background, listen for events, evaluate conditions, and fire other skills automatically.

This is cron. This is systemd. This is the OS primitive that turns prvctice from "a thing I open and use" into "a thing that works while I'm not looking."

### Current State

The infrastructure is 60% there:

- `SkillV2.triggerConfig` field exists with `conditions`, `targetSkillId`, `enabled`
- Event bus emits `trigger:fired`, `trigger:enabled`, `trigger:disabled` (but nothing fires them)
- The action observer already records all event types into a ring buffer
- The skill coordinator has a switch case for `'trigger'` that returns success and does nothing

What's missing: the scheduler, the condition evaluator, and the persistent state.

### Trigger Definition

Extend the existing `TriggerConfig` placeholder into a real interface:

```typescript
// web/types/triggers.ts

interface TriggerConfig {
  // What activates this trigger
  conditions: TriggerCondition[];

  // How conditions combine
  logic: 'all' | 'any'; // AND vs OR

  // What to run when triggered
  targetSkillId: string; // skill to execute
  targetParams?: Record<string, any>; // params to pass

  // Rate limiting
  cooldown?: number; // minimum ms between firings
  maxFirings?: number; // max times this trigger can fire (0 = unlimited)

  // Lifecycle
  enabled: boolean;
  firingCount: number; // how many times it's fired
  lastFiredAt?: number; // timestamp of last firing
}

// A condition is either an event match, a schedule, or a data condition
type TriggerCondition =
  | EventCondition // "when this event fires"
  | ScheduleCondition // "every 30 minutes" / "at 9am"
  | DataCondition // "when weather temp > 90"
  | AppCondition; // "when an app is opened/closed"

interface EventCondition {
  type: 'event';
  eventType: string; // event bus event type to match
  filter?: Record<string, any>; // optional payload filter (shallow match)
}

interface ScheduleCondition {
  type: 'schedule';
  // cron-like but simpler
  interval?: number; // fire every N milliseconds
  cron?: string; // cron expression (minute hour day month weekday)
  // For human readability:
  // "*/30 * * * *" = every 30 minutes
  // "0 9 * * 1-5" = 9am weekdays
}

interface DataCondition {
  type: 'data';
  connector: string; // which connector to query
  method: string; // which method to call
  params?: any; // params to pass
  operator: '>' | '<' | '==' | '!=' | 'contains' | 'exists';
  value: any; // value to compare against
  field: string; // dot-path into the response to check
}

interface AppCondition {
  type: 'app';
  appEvent: 'launched' | 'closed' | 'focused';
  appId?: string; // specific app, or any if omitted
}
```

### Trigger Scheduler

The scheduler runs as a singleton service that manages all active triggers:


### How Triggers Fire

**Event triggers** subscribe to the event bus directly. When a matching event fires, the scheduler evaluates any additional conditions, checks cooldown, and executes the target skill.

**Schedule triggers** use `setInterval` for simple intervals and a minute-resolution timer for cron expressions. The scheduler checks all cron triggers once per minute.

**Data triggers** are polled. The scheduler runs a poll loop every 60 seconds (configurable) that queries connectors for data conditions. Example: "when weather temp > 90°F" polls the weather connector and fires if the condition matches.

**App triggers** listen for app lifecycle events from the app registry (Phase 3). Example: "when PDF Viewer opens, auto-run my Extract skill."

**Recursion guard:** Triggers can cause loops — a trigger fires a skill that opens an app, which fires another trigger, which fires another skill. The scheduler enforces a **recursion depth limit of 3** and a **global firing rate limit of 10 firings/second** across all triggers. Implementation:

```typescript
// In scheduler.ts
const MAX_RECURSION_DEPTH = 3;
const MAX_FIRINGS_PER_SECOND = 10;
let currentDepth = 0;
let firingsThisSecond = 0;

async function fireTrigger(trigger: ActiveTrigger): Promise<void> {
  if (currentDepth >= MAX_RECURSION_DEPTH) {
    console.warn(`Trigger recursion limit hit: ${trigger.skillId}`);
    return; // silently stop the chain
  }
  if (firingsThisSecond >= MAX_FIRINGS_PER_SECOND) {
    console.warn(`Global trigger rate limit hit`);
    return;
  }
  currentDepth++;
  firingsThisSecond++;
  try {
    await skillCoordinator.execute(trigger.targetSkillId, trigger.targetParams);
  } finally {
    currentDepth--;
  }
}

// Reset firingsThisSecond every 1000ms
setInterval(() => {
  firingsThisSecond = 0;
}, 1000);
```

This prevents: trigger A → open app → trigger B → execute skill → trigger A (infinite loop). The depth counter is synchronous and spans the entire trigger chain.

## Phase 10: Universal Search

### What we're building

Spotlight for prvctice. A single search interface that queries across all data stores — conversations, skills, apps, documents, and notes — and returns unified results with the ability to act on them.

Every OS has this. macOS has Spotlight. Windows has Start menu search. Linux has various launchers. The user presses a hotkey, types a query, and gets results from everywhere. prvctice has all the data stores already. This phase builds the single pane of glass.

### Current State

Each data store has its own query mechanism but no unified search:

- **Conversations** — SQLite on backend, searchable by message content
- **Skills** — IndexedDB, searchable by name/keyword/description
- **Apps** — Registry in memory, searchable by name/description/tags
- **Documents** — Registry (from Phase 9), searchable by name/type
- **Notes** — Stored in document storage, content is searchable text

### Ranking Algorithm

Results are scored by a combination of relevance and recency:

```typescript
function rankResults(results: SearchResult[], query: string): SearchResult[] {
  return results
    .map((r) => ({
      ...r,
      score: computeScore(r, query),
    }))
    .sort((a, b) => b.score - a.score);
}

function computeScore(result: SearchResult, query: string): number {
  let score = 0;

  // Exact title match: highest weight
  if (result.title.toLowerCase() === query.toLowerCase()) score += 100;
  // Title starts with query
  else if (result.title.toLowerCase().startsWith(query.toLowerCase())) score += 80;
  // Title contains query
  else if (result.title.toLowerCase().includes(query.toLowerCase())) score += 50;

  // Subtitle/content match
  if (result.subtitle.toLowerCase().includes(query.toLowerCase())) score += 20;

  // Recency boost (logarithmic decay)
  if (result.timestamp) {
    const ageHours = (Date.now() - result.timestamp) / 3600000;
    score += Math.max(0, 30 - Math.log2(ageHours + 1) * 5);
  }

  // Type priority (actions and apps are likely what you're looking for)
  const typePriority: Record<string, number> = {
    app: 10,
    skill: 8,
    document: 6,
    note: 5,
    conversation: 3,
    trigger: 2,
  };
  score += typePriority[result.type] || 0;

  return score;
}
```

## Open Questions

1. **Should generated apps be editable by the user (view source)?** Leaning yes — power users would love it. Show a code editor when they click "Edit" on an app.

2. **Should apps be able to communicate with each other?** Not in v1. Keep them isolated. If we need inter-app communication later, route it through the bridge (app A → system → app B via event bus).

3. **How do we handle apps that need paid APIs?** User configures API keys in settings. Connectors check for valid keys before allowing access. Free alternatives where possible (e.g., Open-Meteo for weather instead of OpenWeatherMap).

4. **~~Vue SFC generation (Tier 2)?~~** RESOLVED: Dropped. All generated/community apps use `type: 'html'`. Builtin apps use `type: 'vue-internal'` (renders directly, no iframe). No compiler needed. If HTML apps hit a ceiling, revisit with vue3-sfc-loader, but this is unlikely given that self-contained HTML + Canvas + WebGL covers everything Nothing Playground does and more.

5. **Should triggers be AI-generatable?** A user says "remind me to check F1 results every race weekend." The AI generates a trigger skill with a cron schedule. This connects Phase 4 (AI generator) with Phase 8 (triggers). Leaning yes — it's the natural extension of "AI builds tools from observed behavior."

6. **Document storage: blobs vs filesystem?** In Electron, we could let documents live on the actual filesystem (user's Documents folder) and index them. In web, everything is in IndexedDB blobs. Should the document layer abstract over both? Probably yes — the `DocumentStorage` union type already supports `type: 'file'` for Electron and `type: 'blob'` for web.

7. **Full-text search indexing?** For v1, simple string matching on titles/names is fine. If the document library grows beyond a few hundred items, we'll need a lightweight search index. MiniSearch (6KB gzipped) or Fuse.js are options. Defer until performance becomes an issue.

8. **Skill marketplace vs app marketplace — unified or separate?** Skills and apps are different things (skills modify behavior, apps are interactive widgets). But from a sharing/browsing perspective, a single "prvctice store" that shows both might be cleaner than two separate galleries. Could be a unified gallery with filters.

9. **Should triggers be able to generate apps on the fly?** Example: a trigger detects the user always checks sports scores on Saturday mornings and auto-generates a "Weekend Sports" app. This connects Phase 6 (recursive learning → app discovery) with Phase 8 (triggers). The recursive learning pipeline already proposes apps — triggers could provide the scheduling for when to check.
